# IMPORTANT (ZeroGPU): the `spaces` CUDA-emulation layer only patches a
# *supported* torch. Per the official ZeroGPU docs the supported range is
# torch 2.8.0 → latest (2.8.0, 2.9.1, 2.10.0, 2.11.0, …). If an out-of-range
# torch gets installed, `spaces` cannot patch it and the forked @spaces.GPU
# worker dies in `worker_init` → `torch.init()` with
# `RuntimeError: No CUDA GPUs are available` (even though the host never
# touched CUDA). Keep torch inside the supported window.

transformers>=5.5.0

# ── bitsandbytes is DELIBERATELY NOT installed on the ZeroGPU Space ──────────
# ROOT CAUSE of the recurring "RuntimeError: No CUDA GPUs are available" inside
# spaces' `worker_init → torch.init() → torch.Tensor([0]).cuda()`:
#
#   bitsandbytes initialises a real CUDA driver context *on import* using its
#   own native ctypes calls (cuInit/cudaGetDeviceCount), bypassing the `spaces`
#   torch-CUDA emulation entirely — so none of the host tripwires catch it.
#   transformers/accelerate import bitsandbytes while loading the model in the
#   host process (their `is_bitsandbytes_available()` checks import the package).
#   Once a CUDA context exists in the host, the forked ZeroGPU worker inherits a
#   broken CUDA state and `torch.init()` dies with "No CUDA GPUs are available".
#
# On ZeroGPU we never use 4-bit anyway (llm_service skips bitsandbytes and loads
# in bfloat16 — see the "skipping bitsandbytes" log line), so installing it here
# is pure downside. Keep it ONLY in backend/requirements.txt for real,
# persistent-CUDA deployments where LLM_LOAD_IN_4BIT is genuinely used.
# DO NOT add bitsandbytes to this (HuggingFace Space) requirements file.
