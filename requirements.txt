# ── Local small language model ─────────────────────────────────
# IMPORTANT (ZeroGPU): the `spaces` CUDA-emulation layer only patches a
# *supported* torch. Per the official ZeroGPU docs the supported range is
# torch 2.8.0 → latest (2.8.0, 2.9.1, 2.10.0, 2.11.0, …). If an out-of-range
# torch gets installed, `spaces` cannot patch it and the forked @spaces.GPU
# worker dies in `worker_init` → `torch.init()` with
# `RuntimeError: No CUDA GPUs are available` (even though the host never
# touched CUDA). Keep torch inside the supported window.
torch>=2.8,<2.12

transformers>=5.5.0
accelerate>=0.30
# ── bitsandbytes: required for 4-bit on dedicated-GPU Spaces (T4/A10G/L4) ────
# This Space can run on a **dedicated GPU** (e.g. t4-small) where the host owns
# a real, persistent CUDA context and ``LLM_LOAD_IN_4BIT`` genuinely loads the
# model with bitsandbytes NF4 quantization. Without this package, model loading
# fails with:
#   "Using `bitsandbytes` 4-bit quantization requires bitsandbytes:
#    pip install -U bitsandbytes>=0.46.1"
#
# Why this is SAFE even though bitsandbytes initialises a real CUDA context on
# import (which historically broke ZeroGPU's *forked* @spaces.GPU worker):
#   * On **ZeroGPU** (SPACES_ZERO_GPU set), app.py poisons the bitsandbytes
#     import slot (``sys.modules["bitsandbytes"] = None``) BEFORE transformers
#     can probe it, and llm_service skips 4-bit entirely and loads in bfloat16.
#     So the dangerous import never runs on a ZeroGPU host.
#   * On a **dedicated GPU** (SPACES_ZERO_GPU unset), there is no forked worker —
#     the host legitimately owns CUDA — so initialising bitsandbytes is exactly
#     what we want.
# The ZeroGPU guards in app.py are now gated on the SPACES_ZERO_GPU env var (not
# merely on `spaces` being importable), so this package is harmless on ZeroGPU
# and necessary on a dedicated GPU.
bitsandbytes>=0.46.1

# ── HuggingFace ZeroGPU (on-demand GPU) ────────────────────────
# Provides the @spaces.GPU decorator. A ZeroGPU Space refuses to start unless
# at least one @spaces.GPU function is detected, and a GPU is only attached for
# the duration of such a call (no persistent CUDA device at startup).

# Use a recent `spaces` release: the ZeroGPU CUDA-emulation/patching layer must
# match the installed torch (>=2.8). Older `spaces` builds only know how to
# patch older torch and will leave a modern torch unpatched, breaking the
# forked worker. Keep this current.
